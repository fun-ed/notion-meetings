# 學習迴圈計畫（2026-10-21）

目標：讓轉錄品質隨使用累積變好。系統只學使用者確認過的內容；新的規則要先通過 benchmark，分數不下降才會自動套用。每台 Mac 各自學習，資料留在本機 `DATA_DIR`。

狀態：P1～P3 已在 0.4.0 實作（D-020）；P4、P5 尚未開始。實作某一階段時，在 [decisions.md](../decisions.md) 新增對應的決策，並更新 [architecture.md](../architecture.md)。和 [可靠度計畫](2026-10-21-reliability.md) 重疊的項目，以這份為準：可靠度計畫第 1 項（真實錄音測試集）是這裡的 P3，第 5 項（跨段落講者比對）是 P5。

## 依據：三段內部會議錄音

2026-10-21 用三段真實的內部會議錄音實測。錄音、逐字稿與人名都不進 repo，這裡只記錄現象。

| 會議 | 長度 | 實際人數 | MAI 分出的講者 | 分講者品質（從內容推斷，未逐句聽寫） |
|---|---|---|---|---|
| 每日站立會議 | 18 分 | 4～5 | 6 位，換人 81 次 | 差：同時有拆錯和併錯；主持人的串場句被分給別人，有 3 個標籤各混了多人 |
| DRI 交接 | 13 分 | 3～4 | 4 位，換人 39 次 | 合理：一人主講約 8.5 分鐘 |
| 架構討論 | 11 分 | 2～3 | 3 位（其中一位只有一聲「啊」） | 合理：以兩人對話為主 |

觀察：

1. **術語誤聽**：站立會議帶上 31 個團隊術語後，下列誤聽都由 MAI 直接聽對：Bation→Bastion、clone job→cron job、Estil→Istio、E case→EKS、run book→runbook，以及 GoAlert 的中文音譯。術語表是目前效益最高的手段。
2. **聽成別的文字系統**：架構討論的逐字稿出現韓文「플랫폼」（platform）。
3. **點名線索**：三場都有，例如「謝謝 X」、「還給 X」、「X 這張（卡）」、「感謝 X 的補充」。多數時候，下一位或上一位講者就是被點名的人。
4. **多人輪流時分講者不可靠**：一人主講的會議分得好，多人快速輪流的站立會議分不好。
5. **試過但無效的調整**：
   - 透過 OpenRouter 傳 `maxSpeakers`：camelCase 寫法回 HTTP 400，snake_case 寫法被忽略。
   - ffmpeg `loudnorm` 音量正規化：講者數與段落數幾乎不變。

## 架構

```text
                       ┌──────────────── data/learned.json（每台 Mac 一份）────────────────┐
                       │ terms[]  團隊術語     rules[]  誤聽改正規則（candidate／active）       │
                       │ voices[] 聲紋（P5）   bench    benchmark 案例與歷次分數              │
                       └───────┬───────────────────┬───────────────────────▲───────────────┘
                               │ 讀取               │ 讀取                  │ 只寫入使用者確認過的
                               ▼                    ▼                       │
上傳 → transcribing ── MAI（phraseList＝會議術語＋團隊術語）                    │
       → OpenCC → 套用 active 規則（保留 raw，記錄 fixes）→ 文字系統檢查（標【?】）   │
       → correcting（Claude 校對，術語＝會議術語＋團隊術語）                          │
       → summarizing（摘要）＋ 講者建議（Claude，只能用名錄與參與者裡的名字）          │
       → done ──► 介面：使用者確認講者建議、校正講者、修改逐字稿文字、加入術語 ──────────┘
                                         │
                                         └──►「凍結為 benchmark」→ eval/bench → 分數趨勢
                                              新規則啟用前先重跑，分數不降才啟用
```

### 資料：`data/learned.json`

用 `auth.js` 的 `jsonStore()` 讀寫，所有修改排隊執行。

```json
{
  "terms":  [{ "term": "Bastion", "source": "meeting:<id>", "addedBy": "<userId>", "addedAt": "<+08:00>", "enabled": true }],
  "rules":  [{ "id": "<uuid>", "from": "Bation", "to": "Bastion", "status": "candidate",
               "confirmations": [{ "meetingId": "<id>", "seg": 12, "userId": "<userId>", "at": "<+08:00>" }],
               "createdAt": "<+08:00>" }],
  "voices": [],
  "bench":  { "cases": [{ "meetingId": "<id>", "frozenAt": "<+08:00>", "frozenBy": "<userId>" }], "runs": [] }
}
```

- `terms`：會議的術語自動累積進來，使用者也可以在逐字稿的【?】附近一鍵加入。介面上可以停用或刪除。
- `rules`：使用者把逐字稿裡的 A 改成 B 時，產生候選規則。同一條規則在 2 場以上會議被確認，而且 benchmark 分數不下降，才變成 `active`。
- `voices`：P5 才使用；格式等 POC 確定後再定。
- `bench.cases`：被凍結的會議。參考答案存在會議資料夾的 `reference.json`（凍結當下的講者與文字），之後再編輯會議也不影響參考答案。

### 處理流程的改動

| 階段 | 改動 | 位置 |
|---|---|---|
| transcribing | `phraseList` 改成會議術語加上團隊術語（去重；數量上限要先查 Azure 的限制） | `transcribe()` |
| OpenCC 之後 | 套用 `active` 規則：完全比對，英數詞要對齊詞邊界；被改到的段落記錄 `fixes: [{ruleId, from, to}]`，`raw` 不變 | 新函式 `applyRules()` |
| OpenCC 之後 | 會議語言是中文時，出現韓文或日文假名就在後面加【?】 | 新函式 `flagForeignScript()` |
| correcting | 校對的術語表同樣加入團隊術語 | `correctTerms()` |
| summarizing 之後 | 另一次 Claude 呼叫，輸出 JSON `speakerHints: [{speaker, name, evidence: [段落號]}]`。名字必須出現在名錄或參與者名單裡，否則丟棄；用量記成 `kind: 'speakers'` | 新函式 `suggestSpeakers()` |

### API 與介面

| 介面 | 內容 | 權限 |
|---|---|---|
| 會議頁講者列 | 顯示「建議：Speaker C = X（第 12、15 段）」，按「套用」才改名 | edit |
| 逐字稿段落 | P4：文字可編輯；改動會詢問是否記成改正規則 | edit |
| 逐字稿【?】 | 「加入團隊術語」 | edit |
| 管理後台「學習」分頁 | 術語、規則（候選、啟用、停用）、benchmark 案例與分數趨勢 | admin |
| 會議頁 | 「凍結為 benchmark」 | owner |
| `GET/PUT /api/learned/terms`、`GET/PATCH /api/learned/rules/:id`、`POST /api/meetings/:id/benchmark` | 對應上面的操作 | 同上 |

### Benchmark

實作時改在伺服器內執行（`runBench()`，由管理後台觸發），直接重用正式的轉錄流程，不另寫 `eval/bench.py`。

- 對每個凍結的案例，用目前的設定重新轉錄（會呼叫 OpenRouter 與 Claude，要手動觸發，不自動執行）。
- 指標：
  - 講者正確率：依時間重疊對齊段落，參考答案與輸出的講者標籤取最佳對應後，計算每段正確的比例。
  - 每 15 分鐘的講者漂移。
  - 文字 CER：去掉標點，簡繁統一後比對。
  - 團隊術語命中數、【?】數量。
- 結果寫進 `bench.runs`，記錄版本、設定摘要與各項分數。管理後台顯示趨勢。
- 合成音檔的 `eval/e2e.py` 維持不變，繼續當快速回歸測試。

## 階段與完成條件

| 階段 | 內容 | 完成條件 |
|---|---|---|
| P1 | 團隊術語表（自動累積、管理介面），文字系統檢查 | 站立會議錄音不帶會議術語重跑，第 1 項的誤聽都被修正；出現韓文時會標【?】；單元測試涵蓋術語合併、文字系統偵測 |
| P2 | 講者建議 | 三段錄音各跑一次：只建議名錄或參與者裡的名字；兩場一人主講的會議，建議和人工判斷一致；沒有按「套用」就不會改名 |
| P3 | Benchmark | 三段錄音由使用者校正後凍結；`eval/bench.py` 輸出各項指標並寫入趨勢；同一設定連跑兩次，分數差距在可解釋範圍 |
| P4 | 逐字稿文字可編輯、改正規則 | 規則需 2 場確認、benchmark 不下降才啟用；啟用後的改動有 `fixes` 紀錄，可以從 `raw` 還原 |
| P5 | 聲紋（設計見下方「P5 聲紋」） | 先做 sherpa-onnx POC：在凍結案例上的認人正確率與誤認率，以及能否打包進 Bun 執行檔。通過後再做建檔（本人同意、可刪除）與比對建議；相似度低於門檻時維持匿名 |

## 實作結果（0.4.0）

用同樣三段錄音、新的暫存實例驗證：
- **P1**：站立會議不填會議術語，只靠 31 個團隊術語，原始辨識就出現 Bastion、cron job、Istio、EKS、runbook、GoAlert，原本的誤聽都沒再出現。架構會議裡的韓文被標【?】。
- **P2**：三場都產生建議，每個都附點名依據的行號。架構會議原本把「Ken 大大」硬配成名錄裡的 Kenny；把 Y leader 加入候選、並要求名字完全一致後，這個錯誤建議消失。
- **P3**：凍結三場後執行 benchmark，耗時 2 分 47 秒、轉錄費用 $0.071。這次的參考答案是未經人工校正的輸出，所以結果（講者 100%、CER 0）只代表同一設定重跑很穩定。真正的準確率要等使用者校正講者後重新凍結。

## P5 聲紋

要解決的問題：多人快速輪流的會議（例如站立會議），MAI 會把同一人拆成兩位，也會把不同人併成一位。聲紋可以做兩件事：
- **認人**：建議某位講者是誰。
- **重新分人**：逐段比對聲紋，修正拆錯與併錯；對站立會議最有幫助的是這一項。

| 階段 | 做法 |
|---|---|
| 建檔 | 成員在「個人設定」自己建立：從已校正的會議挑自己的段落，或錄一段 30～60 秒。只存聲紋向量與來源段落，不另存音訊 |
| 比對 | 對每位匿名講者，取最長的幾段算向量，和團隊聲紋比對；超過門檻才建議並附分數，和點名建議一致時信心更高 |
| 重新分人 | 把每段指派給最接近的聲紋，修正拆錯與併錯；只當建議，使用者確認後才套用 |
| 累積 | 使用者確認講者後，那些段落經本人同意可以加入樣本 |

治理：
- 只有本人能建檔、查看與刪除自己的聲紋；管理員可以停用功能，但不能匯出。
- 只存在本機 `DATA_DIR`，不進 git，不送雲端。
- 每台 Mac 各自一份。跨電腦共享採「本人匯出、對方匯入」，要先確認公司規範。
- 相似度不夠就維持匿名，寧可不認也不要認錯人。

技術：
- 先用 sherpa-onnx POC，量認人正確率、誤認率，以及能不能打包進 Bun 執行檔。
- sherpa-onnx 有 Node 原生模組，也有 WASM 版本；WASM 比較可能放進單一執行檔，或直接在瀏覽器計算。
- pyannote 需要 Python 與 PyTorch，只當備案。
- 經 LiteLLM 轉錄時如果拿不到分講者，這裡的本機分講者就是備案（見 [LLM 端點計畫](2026-10-21-llm-endpoints.md)）。

## 原則

- 只學使用者確認過的內容。系統的建議要使用者按下去才生效。
- 自動改正一定保留原文（`raw`、`fixes`），可以追溯、可以還原。
- 規則、術語、聲紋都可以查看、停用、刪除，並記錄來源會議。
- 不確定時寧可標【?】或維持匿名，也不要猜錯人。
- 學習資料與聲紋只存在本機 `DATA_DIR`，不進 git，不送雲端。聲紋另外需要本人同意。
- 每台 Mac 各自學習。跨使用者共享術語或規則，等使用一段時間後再評估（例如匯出、匯入團隊術語檔）。
