# 團隊知識與品質引導計畫（2026-10-22）

目標：多人中文會議的逐字稿與摘要，持續達到台灣繁中、術語正確、講者正確（D-002）。各團隊的術語、縮寫意思與關注重點只維護一份，並自動送到轉錄、校對與摘要的每一步；Agent 依會議自動建議適合的整理角度，使用者確認後才採用。

狀態：第 1、2 項已完成（D-025，實測見 [研究紀錄](../research/2026-10-22-team-knowledge-correction.md)）；其他是提案。開始實作某一項時，在 [decisions.md](../decisions.md) 新增決策。和 [學習迴圈](2026-10-21-learning-loop.md)、[可靠度計畫](2026-10-21-reliability.md) 重疊的項目，以那兩份為準，這裡只寫串接方式。

## 現況：三份資料各管一段，沒有接起來

| 資料 | 內容（2026-10-22） | 用在哪裡 | 沒用到的地方 |
|---|---|---|---|
| `learned.json` 的 `terms` | 194 個詞，只有拼法（來源：repo 125、cognee 43、會議 26），沒有停用的 | MAI `phraseList`、Claude 術語校對 | 摘要；沒有命中統計，無法判斷哪些詞有用 |
| `knowledge.json`（D-024） | 31 個術語，30 個有意思、29 個誤聽別名，2 條流程筆記 | 摘要的 system prompt | **轉錄與校對**：誤聽別名（例如 Bation→Bastion）沒有告訴校對模型；沒有介面，只能手改 |
| Agent（D-014） | 14 個，提示 50～175 字，都沒有掛 skill | 摘要 | 不知道會議屬於哪個團隊；使用者要自己選 |
| 參與者與名錄（D-012） | 名字、團隊、Y leader | 摘要的負責人、講者建議 | `phraseList` 沒有帶人名，人名聽錯時講者建議也找不到人 |

另外實測 OpenCC `cn→twp` 對已是繁體的文字：「信息、視頻、默認、用戶、服務器、內存、項目」會轉成台灣用詞，「質量、反饋、優化」不會轉。摘要目前沒有經過任何台灣用詞檢查，只靠提示詞要求。

## 原則

沿用學習迴圈的原則，補三條：

1. **一個詞只在一個地方維護。** 術語的拼法、意思、別名、誤聽都寫在團隊知識；轉錄、校對、摘要從同一份資料各取所需。
2. **自動的是建議，確認的才生效。** Agent 選擇、團隊歸屬、新術語，系統只建議；使用者按下去才套用（同 D-018、D-020）。
3. **每個改動都要能量。** 用 benchmark（凍結的真實會議）比較改動前後的講者正確率、CER、術語命中；沒有參考答案前，只做不改變逐字稿文字的改動。

## 項目

### P0：用現有資料、改動小

| # | 項目 | 做法 | 完成條件 |
|---|---|---|---|
| 1 | ✅ 誤聽別名接進術語校對，並驗證 diff | `correctTerms()` 的術語表加上 `knowledge.json` 的別名：「Bation、bastian → Bastion」。同時做可靠度計畫第 4 項的 diff 驗證：每處改動只能改成術語表的詞或加【?】，其他改動丟棄並記警告。兩者一起上，因為別名讓模型更敢改 | 單元測試：別名改對；改成非術語、改寫內容的回覆被丟棄。e2e 嚴苛音檔不低於目前的 45／43～45 |
| 2 | ✅ `phraseList` 加入團隊知識的術語與參與者名字 | `termsFor()` 合併：會議術語 → 參與者名字 → 團隊知識術語 → 團隊術語，沿用 `mergeTerms()` 去重與上限 | 站立會議錄音重跑：人名拼法正確的段落變多；講者建議數量不減少 |
| 3 | 摘要的台灣用詞檢查 | 摘要產生後用 `toTaiwan`（`cn→twp`）轉一次，再用一小份補充詞表（質量→品質、反饋→回饋）。程式碼區塊與英文不動。只改摘要，不改逐字稿（D-006） | 先拿現有會議的摘要離線比對，列出所有被改的地方，人工確認沒有誤改後才啟用 |

### P1：團隊分包與 Agent 自動建議

| # | 項目 | 做法 | 完成條件 |
|---|---|---|---|
| 4 | 團隊知識分團隊 | `knowledge.json` 的 `glossary` 與 `notes` 加選填欄位 `teams: ["SRE"]`，團隊名稱沿用名錄（D-012）。沒寫 `teams` 的是全公司共用。會議的團隊由參與者在名錄裡的團隊決定，帶入「共用＋這些團隊」的知識 | 單元測試：分包合併、舊格式（沒有 `teams`）照常運作 |
| 5 | 摘要只帶逐字稿用到的知識 | 只放 `term` 或 `aliases` 出現在逐字稿的條目，加上所有 `notes`。知識檔變長後，token 不會跟著線性成長 | 單元測試：未出現的術語不帶入；別名命中時帶入正式名稱與意思 |
| 6 | Agent 自動建議 | Agent 加選填欄位 `match`：團隊、標題關鍵字、術語。上傳時依參與者團隊、標題與前幾分鐘逐字稿算分，最高分的顯示成「建議使用：EKS 元件升級（依據：標題、3 個術語）」，按「套用」才換。分數不夠就用使用者原本選的 | 在三段凍結會議與新會議上，建議和人工選擇一致；沒有按套用就不換 |
| 7 | 知識維護介面 | 管理後台「學習」分頁加「團隊知識」：檢視、新增、編輯意思與別名、指定團隊。資料仍存在 `knowledge.json`，不進 git | 介面改動後檔案格式和手動編輯相容；非管理員看不到 |
| 8 | 術語晉升流程 | 從逐字稿【?】或會議術語加入的詞先進 `learned.json`（只有拼法）。「學習」分頁列出「被用過 3 場以上、但還沒有意思」的詞，管理員補上意思後移到團隊知識 | 列表正確；晉升後兩邊不重複 |
| 9 | 術語命中統計 | 每場轉錄結束記錄哪些術語出現在逐字稿（`hits`、`lastHitAt`）。90 天沒命中的詞在「學習」分頁標示，由管理員決定停用 | 統計正確；不自動刪除 |

| # | 項目 | 為什麼要先量 |

## 資料格式（第 4、6 項）

只加選填欄位，舊的檔案不用改：

```json
{
  "glossary": [{ "term": "EKS", "meaning": "AWS 的 Kubernetes 服務", "aliases": ["E case"], "teams": ["SRE"] }],
  "notes": [{ "text": "一句話的團隊流程", "teams": ["SRE"] }]
}
```

- `notes` 同時接受字串（共用）與物件。
- Agent 的 `match`：`{ "teams": ["SRE"], "titleKeywords": ["升級"], "terms": ["EKS", "addon"] }`。內建 Agent 先由管理員補，不自動產生。

## 開會習慣（不用寫程式）

這些做法直接提高講者與術語的正確率，可以寫進團隊的會議守則：

- 開場每人說一次名字；交棒時說「交給 X」。講者建議靠這類點名線索（學習迴圈的觀察 3）。
- 線上會議每人用自己的麥克風；實體會議用一支收音好的麥克風放中間，不要用筆電內建麥克風遠距收音。
- 第一次提到新縮寫時講全名，之後把它加進團隊知識。
- 會後花 2 分鐘確認講者建議與【?】，確認過的內容才會被學習。

## 維護

| 頻率 | 工作 | 負責 |
|---|---|---|
| 每場會議後 | 確認講者建議、處理【?】、把新術語加入團隊術語 | 會議擁有者 |
| 每月 | 「學習」分頁：補新詞的意思（第 8 項）、處理 90 天沒命中的詞（第 9 項）、看 benchmark 趨勢 | 各團隊指定一位知識維護者 |
| 改模型、提示或術語上限時 | 跑 benchmark，分數不降才採用 | 管理員 |

`knowledge.json` 與 `learned.json` 是公司內部資料，只存在各台 Mac 的 `DATA_DIR`，不進 repo、測試或截圖。跨電腦共享仍採手動匯出、匯入（學習迴圈的原則）。
