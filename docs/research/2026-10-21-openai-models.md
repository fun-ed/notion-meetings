# OpenAI 模型評測：gpt-6.1-sol、gpt-6-luna（2026-10-21）

結論：兩個模型都能經 OpenAI 相容端點使用，速度比 Opus 5.5 快很多。預設模型仍維持 Opus 5.5。

| 用途 | 結論 |
|---|---|
| 術語校對 | gpt-6.1-sol 可以用：分數和 Opus 同一水準，但比較敢改，會把不確定的誤聽有把握地改成另一個術語。gpt-6-luna 不建議：嚴苛音檔低於門檻 |
| 摘要 | gpt-6.1-sol 可以用：格式正確、Action Items 解析得到，約 15～19 秒 |

設計見 [LLM 端點計畫](../plans/2026-10-21-llm-endpoints.md)，決策見 D-021。

## 方法

- 端點：magpie 的 OpenAI 相容端點 `http://127.0.0.1:3425/v1`。模型 ID 是 `codex/gpt-6.1-sol`、`codex/gpt-6-luna`；`GET /v1/models` 回傳 86 個模型。
- 測試資料：`eval/e2e.py` 的合成測試組。乾淨與嚴苛兩個音檔各 3 位講者、9 句、45 個術語，見 [benchmark 標準](2026-10-21-benchmark-standards.md)。
- 轉錄一律是 MAI-Transcribe 2，所以兩組的原始辨識結果相同，差別只在校對、摘要與講者建議用的模型。
- 分數抓不到編造，所以另外逐句比對嚴苛音檔的原始辨識、校對結果與參考答案。

## 結果

| 組合 | 乾淨 | 嚴苛 | 校對耗時 | 摘要耗時 |
|---|---|---|---|---|
| 校對 gpt-6-luna、摘要 gpt-6.1-sol | 44/45 PASS | **39/45 FAIL**（門檻 40） | 2.7～3.4 秒 | 14.8～19.4 秒 |
| 校對與摘要都用 gpt-6.1-sol | 45/45 PASS | 42/45 PASS | 9.6～13.1 秒 | 15.2～15.5 秒 |
| 參考：Opus 5.5（同日多次） | 45/45 | 40～45/45 | 真實會議 35～50 秒 | 真實會議 58～67 秒 |

兩組都是 0 簡體、講者 9/9。連線測試：sol 2.3 秒，luna 1.5 秒。

gpt-6.1-sol 校對嚴苛音檔的逐句檢查：
- 改對的：過磁→過 CI、勞費自己→勞退自提、PG-Bouncer→PgBouncer、roll back→rollback。
- **改錯的**：原文是「OAuth 的 refresh token」，MAI 聽成「Postres 的 filter token」。sol 把 Postres 直接改成術語表裡的 Postgres，沒有標【?】。Opus 遇到同一句時標成「Post【?】的 token【?】」，比較保守。
- 沒有出現原文沒有的句子。「0.1%」是 MAI 本身聽錯（原文是「另外算」），不是校對造成的。

## 其他觀察

- 用量：magpie 會在每次請求前加入約 3.3K～4.1K tokens 的提示，記錄成快取讀取。走公司 LiteLLM 時不會有這部分。
- `reasoning_effort` 的 `xhigh`、`max` 不會報錯，但沒辦法確認 magpie 有沒有轉送，所以程式先對應到 `high`。
- 講者建議：合成測試沒有點名線索，兩個模型都正確回傳空的建議。真實錄音的比較還沒做。

## 還沒做

- 用三段真實錄音比較摘要品質與講者建議。
- 用公司 LiteLLM 端點實測（需要端點與測試用的 key）。
- 術語校對的 diff 驗證（reliability 計畫第 4 項）。做完之後，sol 這種「敢改」的問題就能在程式層攔下來。
