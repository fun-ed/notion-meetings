# 公司 LiteLLM 實測（2026-10-21）

結論：
- 文字模型（校對、摘要、講者建議）可以全部改走公司 LiteLLM，用 `npm run start:litellm` 一鍵切換（D-022）。
- 轉錄暫時不行：LiteLLM 上的轉錄模型都達不到 [D-002](../decisions.md) 的基準，所以轉錄仍用 OpenRouter 的 MAI-Transcribe 2。

端點網址與金鑰不寫進 repo；只用合成測試組，沒有送出任何真實會議內容。

## 文字模型

| 項目 | 結果 |
|---|---|
| 模型清單 | `GET /v1/models` 回傳 232 個，包含 `claude-opus-5-5`、`claude-sonnet-5-5`、`gpt-6.1-sol`、`gpt-6-luna` |
| 呼叫 | `POST /v1/chat/completions` 帶 Bearer key，上面四個模型都正常 |
| `reasoning_effort` | 上面四個模型都接受（Claude 由 LiteLLM 轉成 thinking）；本次沒遇到不支援參數的 400 |
| gateway 提示 | 沒有：一句話的請求只有 37～47 個 prompt tokens（magpie 約 4K） |
| 上限 | `GET /v1/model/info` 有 `max_input_tokens`、`max_output_tokens`：Opus、Sonnet 5.5 是 1M／128K；gpt-6.1-sol、gpt-6-luna 是 1.05M／128K |
| 費用 | 每個回應都有 `x-litellm-response-cost` 標頭，另外細分 input、output、reasoning |

在 app 裡實測（`eval/e2e.py`，轉錄走 OpenRouter）：

| 設定 | 乾淨 | 嚴苛 | 校對 | 摘要 | 單場費用（約 1 分鐘的錄音） |
|---|---|---|---|---|---|
| 後台把 Opus 5.5 設成走 LiteLLM | 45/45 | 42/45 | 7.7～14.3 秒 | 約 19 秒 | — |

兩種設定的講者都是 9/9、0 簡體。API key 只在 Opus 那一列存一次，同一個 Endpoint 的其他模型也自動帶上；任何 API 回應裡都找不到 key。

## 轉錄模型

LiteLLM 上有 `gpt-4o-transcribe`、`gpt-4o-mini-transcribe`、`gpt-4o-transcribe-diarize`、`whisper-1`，沒有 MAI-Transcribe。用合成測試組評測，評分方式同 `eval/stt_eval.py`：

| 模型 | 乾淨 | 嚴苛 | 分講者 | 問題 |
|---|---|---|---|---|
| `gpt-4o-transcribe-diarize`（`diarized_json`） | 27/45，10 個簡體字 | 11/45 | 3/3、9/9 | 文字很差，還編出不存在的英文句子；不接受術語提示 |
| `gpt-4o-transcribe`＋術語提示 | 41/45 | 43/45 | 沒有 | 沒有講者與時間戳；嚴苛音檔把「把 HPA 的 CPU threshold 調到百分之七十」改寫成「因為現在的 CPU 使用率超過 70%」 |
| `whisper-1`＋術語提示 | 44/45 | 36/45 | 沒有 | 嚴苛音檔把提示的術語清單原封不動輸出到逐字稿 |
| 參考：MAI-Transcribe 2（OpenRouter） | 45/45 | 40～45/45 | 3/3、9/9 | — |

`gpt-4o-transcribe` 系列的 `/model/info` 寫輸入上限是 16K tokens，長會議很可能要切段。
